# Solution notes

This file records the decisions made while completing the assignment, one section per GitHub issue, so they can be read (and challenged) in one place. Each section says what was chosen, what else was considered, and why.

## #2 PostgreSQL integration and migration test infrastructure

**Separate `integrationTest` Gradle suite.** Database-backed tests live in `src/integrationTest` with their own task, and `check` runs both suites. Considered JUnit tags in one source set (the boundary is only a convention; a forgotten tag puts a Docker test in the fast suite) and putting everything in `test` (every unit-test run would need Docker). The separate suite keeps `./gradlew test` fast, gives CI distinct results per suite, and costs about fifteen lines of Gradle.

**Testcontainers with the production image.** One `postgres:16.2` container per run, declared as a `@ServiceConnection` bean and shared through Spring's context cache. No Docker makes the suite fail rather than skip: a CI run that silently tested nothing would defeat the point of the suite. The application configuration is untouched, so loading the context already proves Liquibase applies cleanly and Hibernate's `ddl-auto: validate` agrees with the schema. Testcontainers is pinned to 1.21.4 because the 1.20.4 that Spring Boot 3.4.2 manages cannot talk to Docker Engine 29 (minimum API version 1.44); 1.21.4 is the last 1.x release and keeps the same artifact names.

**Cleanup by restoring a snapshot rather than transactional rollback.** Tests are not `@Transactional`. A wrapping transaction would hide the behaviour later issues need to observe: open-in-view and lazy loading (#4), and real query counts (#9, since the session cache would absorb repeated reads). Instead a `DatabaseCleaner` copies every table into a `test_baseline` schema once the migrations have run, and after each test truncates the real tables and reloads them from the copy. A first version only deleted rows above the seeded maximum ID; review pointed out that a test which modifies or deletes a seeded row (reachable today by POSTing a customer with an existing ID, which `save` merges) would leak into later tests. Reloading 10,100 rows costs a few tens of milliseconds per test and makes no assumption about ID columns, so it also suits join tables. A guard test compares the cleaner's table list with `information_schema.tables`, so it fails if any table (an entity's or a Liquibase-only join table) is added without registering it.

**Writes are not yet tested.** The seed data inserts explicit IDs without advancing the `BIGSERIAL` sequences, so the first POST collides with ID 1. That is #3, which adds the first write tests on this infrastructure. Rows the tests insert directly use explicit IDs above the seeded range for the same reason.

**Upgrade harness.** `UpgradeDatabase` creates an empty database on the shared container; `LiquibaseRunner` migrates to a named changeset, the test inserts representative rows (names with apostrophes and accents, a customer with no orders, extra orders for an existing customer), then migrates to latest and checks the rows and the foreign key survive. Changesets are addressed by ID so the production changelog carries no test-only tags. Today nothing follows `2-data`, so the harness mostly proves itself; #3 and #7 add the first real upgrade tests. A schema diff between fresh-install and upgrade paths was left out because the changelog is straight-line and both paths cannot differ yet.

## #3 Generated IDs after loading the seed data

**One Liquibase changeset, `3-sequences`, that advances each sequence to `GREATEST(MAX(id), current sequence value)`.** The seed data inserts explicit IDs 1–100 and 1–10,000 without touching the `BIGSERIAL` sequences, so on a fresh database the first POST collided with ID 1. The repair reads the table's highest ID and the sequence's current value from `pg_sequences` and calls `setval` with the larger, so a sequence already ahead of the rows (a deployment that fixed it by hand, or one whose rows were later deleted) is never moved backwards. `pg_sequences.last_value` is `NULL` for a never-used sequence, which sidesteps the trap where a fresh sequence reports `last_value = 1` with `is_called = false`; when both the table and the sequence are empty the repair leaves the next value at 1 rather than skipping it. Considered hardcoding `setval(…, 100)` / `setval(…, 10000)` (wrong for any database already past those values) and switching the entities to `GenerationType.SEQUENCE` with an allocation size (a bigger change to the write path, and it would still need the sequences repaired). The SQL follows the existing `sqlFile` layout so the changelog stays uniform.

**Write coordination.** The changeset runs in a single transaction and starts by locking both tables in `SHARE` mode. Hibernate's identity inserts consume the sequence inside the `INSERT`, so a concurrently running instance (for example the old instance during a rolling deploy) is blocked until the repair commits rather than taking a value between the read and the `setval`. The first version used `EXCLUSIVE` locks taken one table at a time; automated review on the pull request pointed out that an in-flight order insert holds `ROW EXCLUSIVE` on `"order"` and then needs `ROW SHARE` on `customer` for its foreign-key check, so it and the migration would wait on each other and PostgreSQL would abort one of them. Reversing the lock order, as suggested, only moves the deadlock to the other write path: a customer created with nested orders takes `customer` first and then `"order"` through the cascade. The fix is the lock mode rather than the order: `SHARE` still conflicts with `ROW EXCLUSIVE`, so no insert can start, but it is compatible with the `ROW SHARE` the foreign-key check takes, so an insert already past its own table lock can finish. Both locks are taken in one statement, parent first, which is the same order the cascade path uses. The assumption that remains is that nothing calls `nextval` directly or inserts explicit IDs while the migration runs; the application does neither. Nothing in the repair is specific to the seeded values, so it is also safe to rerun as a new changeset if a later data load repeats the mistake.

**Tests.** `GeneratedIdIntegrationTest` POSTs a customer and an order through the real API on the migrated database and asserts the generated IDs land outside the seeded ranges and that the row counts grow by exactly one. IDs are asserted as ranges rather than exact values because `DatabaseCleaner` restores rows but deliberately leaves sequences alone, so values depend on how many writes earlier tests made. `SequenceRepairUpgradeIntegrationTest` uses the #2 upgrade harness to stop at `2-data`, then in one case inserts rows with explicit IDs above the seed and in another advances the sequences by hand; after migrating to latest the next generated IDs are exactly one past the stored rows and one past the advanced sequence respectively, and the existing rows are unchanged. A third test documents the defect itself by showing an insert fails before the repair, so the upgrade tests provably start from a broken state. `SequenceRepairConcurrencyIntegrationTest` holds an uncommitted transaction on each write path (an order insert mid-flight before its foreign-key check, and a customer inserted before its cascaded orders), starts the migration on another thread, waits until `pg_stat_activity` shows it queued on a lock, finishes the write and checks the repair completes with the sequence past the in-flight row. The first of these reproduced the deadlock in about a second before the lock mode was changed. The existing changeset-list assertions now include `3-sequences`.

## #4 Create-request validation and transactional service methods

**Request DTOs instead of entities.** Both controllers bound the request body straight to the JPA entity and called `save`. A client could therefore set `id` and have `save` merge into an existing row, reference a customer that does not exist and get a foreign-key violation back as a 500, or send a 300-character name and get a column-length error as a 500. `POST /customer` now takes `CustomerCreateRequest` (`name`) and `POST /order` takes `OrderCreateRequest` (`description`, `customer: {id}`), validated with Bean Validation against the column constraints: both strings `@NotBlank` and `@Size(max = 255)` to match `VARCHAR(255) NOT NULL`; the customer reference `@NotNull` and `@Valid`, with `@NotNull` on its `id`, so that an absent reference, `"customer": null`, `"customer": {}` and `"customer": {"id": null}` all fail validation rather than reaching the service. `@NotBlank` is stricter than the column, which accepts `""`; a blank or whitespace-only name or description is not a useful record and the old behaviour was never specified. A NUL character is rejected with `@Pattern` because PostgreSQL cannot store it in text, so the insert would otherwise fail as a 500 (found by automated review on the pull request). `@Size` counts UTF-16 code units while `VARCHAR(255)` counts characters, so a value with more than 127 supplementary-plane characters (emoji, rare CJK) is rejected although the column would hold it; the mismatch is only ever over-strict, and a code-point-aware constraint was judged not worth a custom validator for that input. The wire shape of a valid order request is unchanged (`customer` stays a nested object carrying an `id`), so existing well-formed requests keep working.

**Client-supplied IDs are rejected as unknown fields.** The request DTOs list exactly the inputs a create accepts, and `spring.jackson.deserialization.fail-on-unknown-properties` is `true`, so any other property is a 400 before validation runs: `id` on either request, `orders` on a customer, or the `descriptioon` typo in the OpenAPI file. The handler names the offending property in the response (see the error contract below) so the client learns what was rejected. Considered leaving Jackson lenient and dropping `id` silently (the most compatible option, but a client still sending IDs would never learn they are discarded, and the first symptom would be a mismatch between the ID it sent and the one it got back); keeping an `id` field annotated `@Null` (a first draft of this design; it gives the same 400 for a supplied value but accepts `"id": null`, and it would leave `orders` handled by a different rule); and honouring the ID when no row has it (two create semantics in one endpoint, and it reintroduces the sequence drift that #3 repaired). The strict setting is global to the application's `ObjectMapper`, but the application only deserialises request bodies, and the test suites deserialise response DTOs whose fields match the JSON exactly.

**Nested orders on customer create are dropped.** `Customer.orders` has `cascade = ALL`, so the old endpoint could create a customer and its orders from one body. The new request takes only `name`; orders are created through `POST /order`. The OpenAPI file never documented nested orders on customer create, and #8 will require every order to carry at least one product, so keeping a second creation path would mean teaching it the same product rules. The cascade annotation stays on the entity; nothing in the API reaches it now.

**Service layer with the transaction boundary.** `CustomerService` and `OrderService` own both the create and the list paths; controllers validate, delegate and return. `OrderService.create` is `@Transactional`, resolves the customer with `findById` and throws `ReferencedEntityNotFoundException` when it is missing, before anything is written. `getReferenceById` would save the `SELECT` but defer the failure to flush as a foreign-key violation, which is the 500 this issue removes; one extra round trip per create is the price of a clean client error. The lookup cannot protect against a customer deleted between the check and the insert; the foreign key remains the final integrity check, and with no delete endpoint today that window is theoretical, so no locking is added. The response DTO is mapped inside the transaction so any lazy association (products, from #8) loads in the same session. This method is where #8 saves order–product associations, so an invalid product list rolls the order back with it. The list methods moved into the services too, as read-only transactions, so #5, #6 and #9 add their queries in one layer rather than splitting reads and writes between controller and service.

**One error shape.** An `ApiExceptionHandler` extending Spring's `ResponseEntityExceptionHandler` (the same base class that `spring.mvc.problemdetails.enabled` would register; a custom subclass replaces it, so the property is not set) produces every client error as `application/problem+json` with `type`, `title`, `status`, `detail` and `instance`. An `errors` array of `{field, message}` is added whenever a field can be named: Bean Validation failures (one entry per violation) and unknown properties (one entry naming the property, replacing Spring's generic "Failed to read request" detail). Malformed JSON gets a `detail` only, because there is no field to point at. Two further Jackson settings keep the contract honest, both found by review: `parser.strict-duplicate-detection` makes a repeated key a parse error (400) where Jackson 2.18 otherwise reports a second value for a record component as a type-definition error that surfaces as a 500, and `deserialization.accept-float-as-int: false` makes `"id": 7.9` an invalid value (400) instead of silently truncating it onto customer 7. `ReferencedEntityNotFoundException` maps to 422. The resulting contract: 400 for anything wrong with the body itself (malformed JSON, unknown or missing fields, blank strings, lengths, an absent or ID-less customer reference); 422 when the body is well formed but references a customer that does not exist; 404 stays reserved for the resource named in the URL, which #5 needs for `GET /order/{id}`. 400 for the dangling reference as well would also be workable with distinct problem `type` URIs; the status split was preferred because it is visible without parsing the body. 404 for the missing customer was rejected as ambiguous once the order lookup also returns 404. Malformed path variables are already converted to 400 by the base class, so #5 inherits that too.

**Compatibility changes, all intentional.** A supplied `id` is now a 400 (was a silent merge into the existing row). Unknown fields are a 400 (were ignored). Nested `orders` on `POST /customer` are a 400 (were created). Blank `name` or `description` is a 400 (was stored as `""`); a missing one is a 400 (was a 500). An absent or ID-less customer reference is a 400 (was a 500); a reference to a customer that does not exist is a 422 (was a 500). The OpenAPI document is corrected in this issue for what it would otherwise contradict: the two create request bodies now describe the request DTOs with required fields and maximum lengths, the `descriptioon` typo is fixed, and 400 and 422 responses with a ProblemDetail schema are added. The remaining documentation work (lookup, search and product endpoints, README examples) stays with #10.

**Tests.** Controller tests (`@WebMvcTest`, services mocked) cover the 201 path and each 4xx: missing, blank, whitespace-only and over-length fields, a supplied `id`, an unknown field, malformed JSON, each shape of bad customer reference (absent, null, empty object, null ID) and the 422 from the service, asserting the problem body's `status`, `detail` and, where applicable, `errors`. Service tests with mocked repositories cover reference resolution, the exception for a missing customer, and that nothing is saved in that case. `CreateValidationIntegrationTest` runs the scenarios against PostgreSQL where the outcome is observable in the database: supplying a seeded customer's or order's ID returns 400 and that row is unchanged (the acceptance criterion that `save` used to violate), an over-length name inserts no row, an order for a customer that does not exist returns 422 and inserts no row, and a customer body with `orders` returns 400 and inserts nothing. The successful order create, including the stored `customer_id`, is already covered by `GeneratedIdIntegrationTest`. Rolling back a partially written order cannot be exercised until products exist, so that scenario belongs to #8. The order controller test file, previously misnamed `OrderContollerTests.java`, is renamed while it is rewritten.

## #5 Fetching an order by ID

**`GET /order/{id}` returns the existing `OrderDTO`.** The response shape is the same as one element of `GET /order`, including the nested customer, so a client that already parses the list parses the lookup. `OrderController` gains the mapping and delegates to a new `OrderService.findById`, a read-only transaction that maps inside the session like the other read paths from #4. `GET /order` is untouched.

**One statement, through an entity graph.** `Order.customer` is lazy and the lookup response always needs it, so `findById` plus the mapper would cost two round trips per call: one for the order, one for the customer. The repository method `findWithCustomerById` carries `@EntityGraph(attributePaths = "customer")`, so Hibernate joins the customer into the one `SELECT`. A JPQL `JOIN FETCH` query would produce the same SQL; the entity graph was preferred because it states the intent without restating the query, and #8 can extend it with `products` when the response grows. Open-in-view is still at Spring's default, so a missing fetch strategy would not fail, only cost an extra query; the integration test below is what holds the strategy in place.

**404 through a new exception.** `ResourceNotFoundException` maps to 404 with the same problem shape as the other client errors, for example `Order 10001 does not exist`. It is a separate class from `ReferencedEntityNotFoundException` (422) because the two mean different things to a client: the URL names something that is not there, versus the body references something that is not there; #4 reserved 404 for the former. Negative and zero IDs parse as longs and fall through to 404 like any other absent row.

**Malformed IDs name the path variable.** `GET /order/abc` was already a 400 through `ResponseEntityExceptionHandler`, but with Spring's generic detail and no `errors` entry. The handler now overrides `handleTypeMismatch` to produce `Invalid value for 'id'` with an `errors` entry naming `id`, the same shape body-field errors use, so the client learns which part of the request to fix. The same override will cover query parameters in #6. A value too large for a `long` takes the same path.

**Hibernate statistics in the integration base.** `AbstractIntegrationTest` now enables `hibernate.generate_statistics` and exposes `sqlStatementCount()`, with the per-session metrics log silenced so it does not print after every request. This is the first query-count assertion and gives #9 its measurement method. The statistics are per `SessionFactory`, so they are cleared before each test; the suites run tests sequentially, so no two tests share a count. The cost is a small amount of bookkeeping per statement in the test context only; the production configuration is unchanged.

**Documentation stays with #10.** The OpenAPI file does not yet describe the lookup; #4 recorded that lookup, search and product documentation is collected in #10 rather than added piecemeal.

**Tests.** Controller tests with the service mocked cover 200 with the order and customer fields, the 404 problem body including `instance`, and 400 with the `errors` entry for a non-numeric ID and for one that overflows a `long`, checking the service is never called in the 400 cases. Service tests with a mocked repository cover the mapping on a hit and the exception on a miss. `OrderLookupIntegrationTest` against PostgreSQL reads seeded order 1 with its customer, asserts the lookup prepares exactly one SQL statement (verified to report two with the entity graph removed), returns 404 for the first ID above the seed after checking no such row exists, and returns the 400 for a malformed ID through the real handler chain. The list endpoint's continued behaviour is already covered by `SeedDataIntegrationTest`, which reads all 10,000 orders.
## #6 Customer name substring search

**`GET /customer?q=…` filters by words of the name; omitted or blank `q` is the unchanged listing.** The query is cut into whitespace-separated words and a customer matches when every word is a case-insensitive substring of their name, in any order: `ann` matches `Dianne Lemke`, `Lance Stiedemann Sr.` and `Angelo Pfannerstill`; `ed glover` and `glover ed` both match only `Ed Glover`. The README asks for "a substring of one of the words in their name", and a word of the query contains no whitespace, so any match necessarily lies inside one word of the name; nothing further is needed to enforce the boundary. Three readings of a multiword query were considered: requiring every word (chosen; it is what a search box does, and it keeps each word inside a name word), matching the trimmed query literally against the whole name (`anne sm` would then match `Joanne Smith` across the boundary, which the README wording excludes), and rejecting internal whitespace with a 400 (strictest, but it turns a natural `first last` query into an error). A query with no words at all (absent, empty or only whitespace) is not a search and returns every customer rather than a 400, because the empty substring matches everything and the client that trims its input should see the same result as the one that omits the parameter. The response is the existing `CustomerDTO` list with the nested orders, so a client that parses the listing parses the search; there is no ordering guarantee, as there is none on the listing. There is no new error case: any string is a valid query, and one longer than any name simply matches nothing. Whitespace means Unicode white space (`\s` with `UNICODE_CHARACTER_CLASS`), so a non-breaking space separates words as a plain space does, and empty words are dropped, so no stray separator can produce the `%%` pattern that matches everyone. One quirk is documented rather than handled: a repeated parameter, `q=a&q=b`, binds as the single string `a,b` under Spring's default conversion and so matches nothing.

**Filtering happens in the database, through a specification.** `CustomerRepository` also extends `JpaSpecificationExecutor`, and `CustomerSpecifications.nameContainsEachOf` builds one `WHERE … AND …` with a `LIKE` per word, so the number of words needs no fixed-arity query method. The alternative of loading all customers and filtering in Java would read every row and its orders for each search, which is the opposite of what #9 is about. Case folding is left to the database so that one collation defines it: Hibernate's `HibernateCriteriaBuilder.ilike` renders `name ilike ? escape '\'` on PostgreSQL and binds the pattern. The portable JPA spelling, `lower(name) like lower(literal)`, was tried first and rejected after reading the generated SQL: `CriteriaBuilder.literal` is inlined into the statement text (escaped by Hibernate, so not injectable, but a distinct statement per search and the shape a security review flags), and the JPA builder has no case-insensitive `like` of its own. Folding the pattern in Java with `Locale.ROOT` and binding it with the plain `like` overload would also have worked and is pure JPA, at the cost of two definitions of lower case; the single cast to Hibernate's builder was preferred because the application already depends on Hibernate for its statistics, batch fetching and schema validation. `%`, `_` and `\` in a word are escaped and matched literally with `ESCAPE '\'`, so `q=%` finds the one customer whose name contains a percent sign rather than all of them, and `ann_` does not match `Dianne`. An apostrophe needs nothing special because the value is a bound parameter. The `name` attribute is addressed by string, as there is no generated metamodel in the project; the integration tests would catch a rename.

**A NUL in the query matches nothing, without a round trip.** Automated review on the pull request pointed out that `q=%00` reached the database: a NUL is a legal character in a Java string but PostgreSQL cannot hold one in a text value, so binding it raised an error that surfaced as a 500. The review suggested rejecting it with a 400 as the create requests do (#4). That was considered and not followed: the create path rejects NUL because the value would be stored, whereas a search value is never stored and the search has no other client-error case; any other character that no name contains, `q=zzzz` or a control character, yields an empty list. A NUL is simply a character no stored name can contain (the column cannot hold it and #4 keeps it out), so the truthful answer is the same empty list, and it is given before the repository is called because the round trip could only fail. A 400 would also have needed method validation on the query parameter and a handler override to keep the `errors` shape; that machinery is not worth adding for a value whose correct result is already known.

**No index in this issue.** A `LIKE '%word%'` cannot use a b-tree index whatever the collation, and the seeded 100 customers are scanned in well under a millisecond. A trigram index (`pg_trgm`, GIN) is the standard remedy at scale and would be a migration; #9 is where query plans are inspected and indexes justified, so the decision is recorded there rather than pre-empted here. The nested orders of each matched customer load as they do for the listing, lazily inside the read-only transaction with the configured batch size; the search does not change that strategy, and #9 covers it for both endpoints.

**Documentation stays with #10,** as for #4 and #5: the OpenAPI file does not yet describe `q`.

**Tests.** `CustomerSpecificationsTest` covers the pure parts: null, empty and whitespace-only queries (including non-ASCII spaces) have no words; surrounding whitespace is dropped and any run of whitespace splits; words keep their case; each wildcard character and the backslash are escaped in the pattern; an empty word list is rejected. `CustomerServiceTest` checks that a blank query takes the unfiltered path without building a specification and that a query with words goes through the specification and is mapped. `CustomerControllerTests` check that an absent parameter reaches the service as `null`, that a padded or empty value reaches it untouched (trimming is the service's job), and that no matches render as `[]`. `CustomerSearchIntegrationTest` against PostgreSQL covers a substring at the start, middle and end of a word (`kut`, `utc`, `tch` for `Vicki Kutch`), a substring inside any word (`ann`), a padded mixed-case query, no matches, omitted and blank queries returning all 100, both orders of `ed glover` plus a third word that excludes everyone, and customers inserted above the seeded range with an apostrophe, `%`, `_` and `\` in their names, including the percent sign arriving URL-encoded. It also checks that a matched customer is identical, orders included, to the same customer in the unfiltered listing and carries as many orders as a JDBC count, and, through Hibernate's entity-load statistics (`entityLoadCount` is added to the integration base next to #5's statement count), that a search for `ann` loads three `Customer` entities rather than a hundred, which is what fails if the filter ever moves into Java. A NUL arriving URL-encoded or inside a word returns `[]` with no SQL statement issued; the same case is checked at the unit level for the word predicate and for the service never touching the repository.

## #7 Product persistence and order–product relationships

**Schema.** One changeset, `4-products`, in the same `sqlFile` layout as the first three. It creates `product` (`id BIGSERIAL`, `description VARCHAR(255) NOT NULL`, the same shape as the customer and order columns so #8 can apply the #4 validation rules unchanged) and `order_product` (`order_id`, `product_id`, both `NOT NULL`) with foreign keys to `"order"` and `product`. The join table's primary key is the `(order_id, product_id)` pair, which does two jobs with one object: the same association cannot be stored twice, and the leading column indexes the order-to-products direction. A second index on `product_id` serves the product-to-orders direction that the product endpoints in #8 walk. A surrogate `id` plus a unique constraint was considered and rejected because nothing would ever read the surrogate. Both foreign keys keep PostgreSQL's default `NO ACTION` behaviour, which refuses the delete as `RESTRICT` would: a product still in an order cannot be deleted out from under it, and an order's associations are removed by the application when it deletes the order (nothing does today; if a delete endpoint arrives, `ON DELETE CASCADE` on `order_id` is the decision to revisit). The changeset is additive and reads, rewrites and backfills nothing. It is not lock-free, though: adding a foreign key takes a `SHARE ROW EXCLUSIVE` lock on the referenced table, so for the changeset's transaction `"order"` is locked against inserts. An order insert already in flight on the previous release finishes first (the changeset waits for its `ROW EXCLUSIVE` lock), and inserts arriving afterwards wait the few milliseconds two `CREATE TABLE`s take. The customer table is not locked, so the deadlock shape #3 had to design around (an insert holding `"order"` while waiting for `customer`) cannot occur. The first draft of this paragraph claimed the changeset took no lock beyond `CREATE TABLE`'s own; the reviewer corrected it. Liquibase's YAML `createTable` syntax was considered for this changeset and rejected to keep the changelog uniform. No products are seeded: the seed data has no product information, and #8 and #10 provide demonstration data through the API.

**Mapping.** `Order` owns the relationship: a lazy `@ManyToMany` `Set<Product> products` over `@JoinTable(order_product)`, no cascade, because products outlive the orders that contain them. `Product` carries the lazy inverse `Set<Order> orders` with `mappedBy = "products"`. Owning side on the order means #8 creates an order and its associations by saving the order inside the transaction `OrderService.create` already has, so an invalid product list rolls the order back with it. Sets rather than lists: with bag semantics the same product could be added twice in memory and fail against the primary key at flush, and Hibernate refuses to fetch two bags in one query (`MultipleBagFetchException`), which #9 would meet as soon as products are fetched alongside a customer's orders. Both sets carry `@OrderBy("id")`: Hibernate then backs them with an insertion-ordered set loaded in ID order, so iteration is the same on every call and every instance, and the arrays #8 serialises from them are stable without a sort in the mapper; a plain `HashSet` of identity-hashed entities iterates in an order that changes between JVM runs. A dedicated `OrderProduct` join entity was considered and rejected as unnecessary while the join carries no attributes; quantities or pricing, if they ever arrive, add columns to a table whose key is already the pair. `ProductRepository` is a plain `JpaRepository` with no custom queries; #8 and #9 add what the endpoints need.

**`Order` and `Product` no longer use Lombok's `@Data`.** This was planned as a hygiene change and turned out to be a correctness one. With `@Data` on both entities, five of the eight mapping tests failed on the first run: four with Hibernate's own consistency assertion in `PersistentSet.initializeEmptyCollection`, because adding a `Product` to the order's set called the generated `hashCode`, which includes the lazy `orders` collection and initialised it in the middle of the load; and one showing that putting an `Order` into a `HashSet` issued two extra statements, for the customer proxy and the products. The original code's `@Data` on entities is one of its deliberate bad choices, and it had not bitten before because no entity had ever been hashed or placed in a set. Both classes now use `@Getter` and `@Setter` and inherit identity equality, which is the correct semantics when instances only ever meet inside one persistence context, as they do here: sessions are per request and nothing merges detached instances. Two alternatives were considered. Excluding each relationship field with `@EqualsAndHashCode.Exclude` works but has to be remembered for every new association, and still hashes `description`, so an entity's hash changes when it is updated. ID-based equality with a constant `hashCode` is correct across persistence contexts but adds code for a case the application does not have. `Customer` keeps `@Data` because nothing hashes a customer; it is on the list for #9 if the fetch work there puts customers in a set.

**Legacy orders.** No association is invented for the 10,000 seeded orders or for any order in a production database: after the upgrade every existing order has zero rows in `order_product`, the mapping reads that as an empty set, and #8 serialises it as an empty list. The rule that an order carries at least one product applies to orders created from #8 onwards and lives in the application, not the schema, because a minimum row count in a child table cannot be expressed as a plain constraint (it would need a trigger or a deferred check) and every existing order would violate it on the day it was added. Rollout implications: the tables are additive, so an instance still running the previous release during a rolling deploy ignores them (Hibernate's `ddl-auto: validate` only checks the tables it maps, so the extra ones are invisible to it); any order that instance creates during the window has no products and falls under the same legacy rule; and because no backfill is planned, clients of the order endpoints must accept an empty product list indefinitely, not just for the migration period. If the business later decides every order must have products, that is a data migration with product information the project does not hold, so it is recorded as a possible follow-up rather than done. The product sequence starts at one because nothing is seeded, so the #3 repair is not needed for it.

**Documentation stays with #10,** as for the earlier issues: the README's data-model paragraph and the OpenAPI file still describe the pre-product model until the endpoints exist.

**Tests.** The two changeset-list assertions now include `4-products`. `ProductSchemaIntegrationTest` checks the schema at JDBC level, independently of the mapping: one product in two orders and two products in one order both store, the same pair twice is a `DuplicateKeyException`, a reference to a missing order or product fails on the named foreign key, deleting a product that an order contains is refused, a product without a description is refused, and `pg_indexes` shows the pair index and the `product_id` index. `ProductUpgradeIntegrationTest` uses the #2 harness to stop at `3-sequences`, add customers and orders as a production database would hold, migrate to latest and check the counts are unchanged, both new tables are empty, no pre-existing order has an association, a legacy order can then be given a product whose generated ID is one, and a fresh install also arrives with empty product tables. `ProductMappingIntegrationTest` runs each scenario inside a `TransactionTemplate`, as a service method would: saving a new order for an existing customer with two existing products writes exactly those join rows and inserts no further product (the path `OrderService.create` takes in #8; the reviewer pointed out the first version only exercised dirty checking on managed orders), adding products to a managed order writes them at commit, adding the same product twice stores one row, both sides read the other back and the order side iterates in ID order whatever order the rows were inserted in, looking an order up by ID prepares one statement and leaves `products` uninitialised until it is touched (then exactly one more), looking a product up leaves `orders` uninitialised, and placing either entity in a `HashSet` issues no statement and initialises nothing, which is the test that fails with `@Data`. `DatabaseCleaner` registers the two new tables, children first, so its guard test passes and every test above is restored to the seeded state. `OrderLookupIntegrationTest`'s one-statement assertion from #5 continues to hold through the API, so the lookup path is proven not to fetch products eagerly.

## #8 Product endpoints and products in orders

**Endpoints.** `POST /products`, `GET /products` and `GET /products/{id}`, at the plural path because the README task and the OpenAPI file both name it that way; it is inconsistent with `/order` and `/customer`, and following the written specification was preferred over tidying it, with no alias added. `ProductCreateRequest` carries only `description` under the #4 rules (`@NotBlank`, `@Size(max = 255)`, no NUL; `id` or `orders` in the body is an unknown field, 400). `ProductDTO` is `{id, description, orders}` where `orders` is the ascending list of containing order IDs: the README asks for the IDs, and an order's own representation would make the graph circular. The IDs cannot repeat because the join table's key is the pair (#7). A product in no order carries `[]`. The lookup answers 404 through `ResourceNotFoundException` and a malformed ID 400, both from the #5 handler. A new `ProductService` and `ProductMapper` follow the customer and order stacks exactly.

**Orders take `products: [{id}, …]`.** The shape mirrors the existing `customer: {id}` reference, so unknown fields inside an element (`{"id": 1, "description": …}`) are rejected the same way, with the path `products[0].description`. Bean Validation rejects an absent, null or empty list (`@NotEmpty`, field `products`), a null element (`products[0]`) and an element without an ID (`products[0].id`). `OrderService.create` resolves the customer as before and then every product in one `findAllById`; any ID without a row makes it throw `ReferencedEntityNotFoundException` (422) naming every missing ID in ascending order, `Products 7001, 7002 do not exist`, so a client fixes the whole request in one round trip. The order and its `order_product` rows are then saved in the one transaction #4 set up, and because both checks precede the first write, an invalid request writes nothing rather than something to roll back; the foreign keys stay as the final check against a product deleted between the lookup and the insert, a window that is theoretical while nothing deletes. The cost of a create is therefore one statement for the customer, one for the products, the order insert and one join-row insert per product: five for two products, which the integration test asserts. `ProductReference` (one `@NotNull` ID) is a separate record from `CustomerReference` although identical today, so a later product-specific field does not land on the customer. `GET /customer` is unchanged: the issue names the order endpoints, and the customer listing already carries all 10,000 orders; whether it should carry products as well is a question for #9, where its payload is measured.

**A repeated product ID is a 400,** field `products`, message `must not contain the same product more than once`, through a small `@DistinctProducts` constraint. Quantities are outside the model, so `[{"id": 1}, {"id": 1}]` has no meaning the server can represent; collapsing it silently would hide what is most likely a client bug, which is the same reasoning that made unknown fields and duplicate JSON keys errors in #4. The alternative, storing the association once and returning one product, was rejected for that reason. If the request bypassed the constraint the entity's `Set` and the join table's primary key (#7) would still store one row, so the policy is defence in depth rather than the only guard. The constraint's `@Target` has to include `FIELD`: javac copies a record-component annotation onto the backing field, which is where the validator looks, only when the target allows it; a first version targeted `RECORD_COMPONENT` alone and the controller test for the duplicate case is what caught it, as the request went through as 201.

**Order responses gain `products`,** a list of `{id, description}` (`OrderProductDTO`) in ascending ID order, on the create response, the lookup and the list; `CustomerOrderDTO` inside the customer listing does not change. A product's own containing orders are left out so the graph stays finite, as `OrderCustomerDTO` does for the customer. A legacy order serialises `[]` under the #7 policy, which the clients must accept indefinitely. The two mappers sort explicitly (`Comparator.comparing(Product::getId)` and `sorted()` on the IDs), which #7 had hoped to avoid through `@OrderBy`: the first unit test with a plain `HashSet` came back in identity-hash order, which showed that the order would otherwise be a property of how Hibernate happened to load the collection rather than of the mapping. On a set that is already sorted the sort is linear, so it costs nothing measurable and makes the contract hold for any collection the entity carries.

**Fetch strategy: one statement per read.** The #5 lookup graph becomes `{customer, products}` (`findWithCustomerAndProductsById`), the list gets the same graph through a new `findAllWithCustomerAndProducts`, and the two product reads carry `orders` (`findAllWithOrders`, `findWithOrdersById`). The list methods spell out their JPQL (`select o from Order o order by o.id`) because Spring Data would otherwise parse the `And` and the `Or` in the method names as predicates, and because the fetch join needs a root ordering: Hibernate appends a fetched collection's `@OrderBy` to the SQL, so without `order by o.id` the order list came back sorted by each order's lowest product ID with the legacy orders last, and the product list by each product's lowest order ID. Review caught this; two tests now reproduce it (an order deep in the list given the lowest product ID, and a lower product ID placed in a later order) and both lists are ascending by their own ID. That is the first ordering guarantee either listing has had; previously they returned heap order, which for the seeded data happened to be ID order, so no client should notice. The list was given its graph in this issue rather than left to #9 because adding products to the response with only the configured batch fetching would have added about a thousand statements (10,000 orders in batches of ten) to an endpoint that previously needed only the orders plus the hundred customers in batches of ten; shipping that regression to be measured later was not worth the cleaner before-and-after story. Fetch-joining a collection returns one row per association and repeats the order and customer columns on each, which Hibernate 6 reduces to one root per order; the integration test asserts 10,000 distinct orders. What is deferred to #9 is the payload evidence: for orders with many products a DTO projection or a second batched query may beat the wide join, and the product side loads `Order` entities (ID, description, customer ID) to produce IDs that a `select p.id, o.id` projection would give in a second statement of narrow rows. One statement was chosen because latency per round trip is the stated production problem, and the decision is recorded so #9 can revisit it with numbers. The customer listing and search keep their #6 strategy until then.

**Compatibility.** `POST /order` without `products` was a 201 and is now a 400 naming `products`; a client that has not been updated gets a documented error rather than an order it will later find invalid. The response shapes are additive (`products` on orders); existing fields and the problem format are unchanged. The OpenAPI file and the README's data-model and endpoint paragraphs still describe the pre-product API; #10 collects that documentation, as #4 to #7 decided. An instance of the previous release running during a rolling deploy accepts product-less orders for the length of the window, which fall under the legacy policy; nothing here changes the schema, so no migration lock is taken.

**Tests.** `ProductControllerTests` (service mocked) cover 201 with an empty `orders` array, the list and lookup bodies, 404, the 400 for a malformed ID, and each body error: missing, blank, NUL and over-length description, a supplied `id`, supplied `orders`, malformed JSON. `OrderControllerTests` is rewritten for the new body: 201 with products, products on the list and lookup, the legacy empty array, the 422 naming several products, and a 400 for each of absent, null and empty `products`, a duplicate, an empty element, a null element, a non-numeric element ID, `products` that is not an array, an unknown field inside an element, and three violations reported together sorted by field. `ProductServiceTest` and `OrderServiceTest` (repositories mocked) cover the mapping including ID ordering, that `save` receives no client ID and the resolved entities, that a missing customer stops before the product lookup, and that one or several missing products throw with nothing saved. `ProductApiIntegrationTest` against PostgreSQL covers the stored row and empty `orders` on create, an over-length description inserting nothing, the empty list before any product exists, ascending non-duplicated order IDs for a product associated newest-order-first, `[]` for an unused product, 404 and the malformed ID through the real handler, and that the list of 25 products with two orders each and the lookup each prepare exactly one statement. `OrderProductsIntegrationTest` covers a create storing exactly the requested join rows and returning products in ID order whatever order the body listed them, one missing product (422, no order row and no join row), several missing products named together, a duplicate (400, nothing written), the pre-#8 body (400), a missing customer writing no association, the lookup with products in one statement, a legacy order's empty list, and the 10,000-order list carrying each order's products with no duplicated roots in one statement. Removing the collection paths from the entity graphs makes exactly the four one-statement assertions fail, which is how they were shown to measure the fetch strategy. `GeneratedIdIntegrationTest` and `CreateValidationIntegrationTest` now create a product before posting an order, and `ProductMappingIntegrationTest`'s lazy-loading check uses the plain `findById`, since the lookup method it used now fetches products by design.

## #9 Reducing database round trips on the GET endpoints

**What was left to do.** #5 and #8 had already given the order and product reads a single statement each, so this issue is the customer reads, which still loaded orders lazily in batches of ten, and the evidence the earlier issues deferred: measured counts and timings under latency, query plans, the payload cost of the wide joins, and whether any index is justified. The README's task is "the database is not co-located with the application server", so the quantity that matters is round trips per request, and the measurement was built to count those rather than to trust Hibernate's statement count.

**Measurement method.** `./gradlew latencyBenchmark` runs `LatencyBenchmarkIntegrationTest` against its own `postgres:16.2` container behind a Toxiproxy container, and writes `build/reports/latency-benchmark.md`. The dataset is the Liquibase seed (100 customers, 10,000 orders) plus `LargerDataset`: one customer with no orders, 1,010 products, and three products on every order whose ID is not a multiple of seven, which leaves 1,428 legacy orders with none and ten products in no order (25,716 `order_product` rows). The same loader is used by the regression tests. Each of seven requests is sent twice to warm up, then once to collect counts, then five times without latency and five times with a latency toxic of 25 ms in each direction, so one round trip costs about 50 ms; medians are reported. Four figures are read per request: statements prepared, from Hibernate's statistics; statements executed and rows returned, from PostgreSQL's own `pg_stat_statements` (reset before the request, the statistics queries excluded by text); the plan of every `SELECT`, from `EXPLAIN (ANALYZE, BUFFERS)` with the bound parameters replaced by the scenario's literals; and the response body as raw bytes from `java.net.http.HttpClient`, which never decompresses, once without and once with `Accept-Encoding: gzip`. The result size between PostgreSQL and the application is estimated as actual rows times the planner's row width and is labelled an estimate throughout; nothing reports the bytes on that wire. The decisive column is derived round trips: the difference between the medians with and without latency divided by the round-trip cost, which counts what actually crossed the network, transaction chatter included. Timings are never asserted, in CI or anywhere; the benchmark is excluded from `check` and run by hand. The numbers below are from one Windows machine with Docker Desktop and are reproducible in shape, not in milliseconds.

The search for `ann` matched three customers and cost three round trips. Every other request cost two, which is the subject of its own paragraph below.

**Customer reads in one statement.** `CustomerRepository` redeclares `findAll(Specification, Sort)` with `@EntityGraph(attributePaths = "orders")`; Spring Data applies the graph to the criteria query it builds for a specification exactly as it does to a derived method, so the listing (`CustomerSpecifications.all()`, a specification with no predicate) and the search (`nameContainsEachOf`) share one method and one SQL shape: a `left join "order"` with the customer filter in the `where`. This is the technique #5 and #8 used; a DTO projection (`select new …(c.id, c.name, o.id, o.description)` grouped in Java) was considered and would skip entity hydration for the 10,000 orders, but it bypasses the mapper the other reads use and the entity approach measured at 28 ms end to end, so there was nothing to buy. Both callers pass `Sort.by("id")`, for the reason #8 found: Hibernate appends the collection's `@OrderBy` to the SQL, so without a root ordering the customers come back sorted by their lowest order ID. `Customer.orders` gains `@OrderBy("id")`, and `CustomerMapper` sorts the nested orders explicitly as the other two mappers have since #8, so the ascending order is a property of the mapping and not of how the list was loaded; `CustomerMapperTest` feeds it an unsorted list. What the join costs is the repeated customer columns: the estimate is 610 KB from the database for the listing where the batched statements moved about 382 KB (101 rows of width 23 plus 10,000 of width 38), roughly 60 % more bytes for eleven fewer round trips, which at any latency above a millisecond or so is the right trade.

The customer listing went from 13 round trips to 2 and from 705 ms to 127 ms under the simulated latency; the search from 3 to 2. The `DB statements` column counts `BEGIN READ ONLY` where `pg_stat_statements` happened to record it; derived round trips is the measure to read. No request now prepares a number of statements that depends on the data, which is the issue's criterion; `ReadQueryCountIntegrationTest` holds it in place, as described under Tests.

**Two round trips per request remain, by choice.** Every read is a `@Transactional(readOnly = true)` method, and the JDBC driver sends `BEGIN` together with the first statement but `COMMIT` on its own, so a one-statement request costs two round trips: for a lookup under 25 ms latency, 107 ms of which about 100 is the network. Running the reads in autocommit mode, without a transaction, would halve that. It was not done: the issue asks for responses mapped within deliberate transaction boundaries, the read-only transaction is what gives the mapping its persistence context, and #4 made the service methods transactional on purpose. What the transaction does not give is a transaction-wide snapshot: the isolation level is PostgreSQL's default `READ COMMITTED`, under which each statement sees the data committed when it started, so a transaction of several statements could see different states. The reads are consistent because each is one statement, not because of the transaction; the guarantee would hold in autocommit mode too, and only `REPEATABLE READ` would extend it across statements if a read ever needed more than one. The option is recorded here with its price, one round trip per read, so it can be taken deliberately if the lookups' latency ever matters more than the boundary. Connection validation by the pool (`isValid`, after an idle gap) is a further occasional round trip that the medians do not show; it is also left alone.

**One index, justified at scale rather than on the seed.** The expectation was that the search path, which filters customers first and then needs their orders, would use an index on `"order".customer_id`, the one foreign key without an index. On the seed it does not: 10,000 orders fit in 85 pages and every customer's orders are scattered across all of them, so the planner's hash join over a sequential scan (0.9 ms, 86 buffers) is cheaper than any index path, and the plans with and without the index are identical. The benchmark therefore ends with a scale experiment: 10,000 further customers holding 990,000 orders scattered the same way, `ANALYZE`, and the search SQL the application really issues explained with and without the index. A search matching ten customers takes 3.1 ms and 1,095 buffers with the index (bitmap scan per customer) against 73.1 ms and 8,410 buffers without (a sequential scan of the million rows for every search, however few match). A search matching all 10,000 scale customers, which returns 990,000 orders, is slower with the index: the planner chooses a merge join driven by an index scan (679 ms, 997,230 buffer hits) over the hash join with an external sort it used before (480 ms, 74 MB of temporary file). Those are the two sides: the index makes a selective search scale with its matches instead of with the table, and makes a search that returns most of the table about 40 % slower. A search that returns most of the table is already a 50 MB response that no client should be asking for, so the index is added. The customer name search itself stays without an index for the reason #6 gave: `ILIKE '%…%'` cannot use a b-tree, a trigram index needs the `pg_trgm` extension, and the customer table is one page.

**The index migration is built concurrently and fails loudly.** `5-order-customer-index` runs `CREATE INDEX CONCURRENTLY` with `runInTransaction: false`, because a plain `CREATE INDEX` holds a `SHARE` lock on `"order"` for the whole build and blocks every order insert from an instance still running, while a concurrent build only blocks other DDL; the earlier migrations took the same care over locks. A concurrent build that fails or is interrupted leaves an invalid index of that name behind, and `IF NOT EXISTS` is deliberately not used: it would let the retry succeed and record the changeset with an index the planner never reads. Instead the retry fails with "relation already exists" until someone runs `DROP INDEX idx_order_customer_id`, which the SQL file says. `OrderCustomerIndexIntegrationTest` checks the index exists and `pg_index.indisvalid` is true after the changelog runs, and the existing upgrade tests apply the changeset over databases holding rows.

**The wide joins stay, with their crossover recorded.** This is the question #8 deferred. For the order list the estimate is 2.39 MB from the database for a 2.08 MB body: one row per order–product pair with the order and customer columns repeated, about 15 % over the body, which a second statement would not improve on by enough to pay for a round trip. The product list is the other way round: an estimated 1.88 MB from the database for a 176 KB body, because `Product.orders` is a set of `Order` entities and the join carries each order's description and customer ID (width 73) only for the mapper to keep the ID. A narrower result is available without a second statement: a scalar projection over the same left join, `select p.id, p.description, o.id from Product p left join p.orders o order by p.id, o.id`, returns one row per product–order pair of about 30 bytes, under 1 MB for the benchmark dataset, and the mapper groups the rows into DTOs in Java. (A separate `select product_id, order_id from order_product` would be narrower still, about 400 KB, but as a second statement it costs the round trip this issue is about.) The projection was not taken: it replaces entity loading with hand-written grouping code and a second repository method shape, for a saving of under 1 MB per request that, with the README naming latency and not bandwidth as the problem, nothing yet needs. It is a contained change to `ProductRepository` and `ProductMapper` if bandwidth turns out to be the constraint; the benchmark report gives the inputs. Products are not added to the customer response: nothing asks for them, the customer listing is already a 504 KB body carrying every order, and the figures above show what each further collection in a fetch join costs.

**gzip, measured separately from the database changes.** `server.compression.enabled: true` for JSON and problem JSON. Every timing in the tables was taken without `Accept-Encoding`, so compression affects none of them; the `gzip bytes` column is its own measurement. The order list goes from 2,079,280 to 240,500 bytes, the customer listing from 503,515 to 75,012, the product list from 176,050 to 36,183, roughly a factor of five to nine, because the bodies repeat the same keys ten thousand times. This helps the application-to-client leg only; the database-to-application transfer is unchanged. One detail found by the test: Tomcat applies its minimum size (2 KB by default) only when it knows the `Content-Length`, and Spring streams JSON chunked, so a 208-byte lookup is gzipped as well (to 149 bytes). That is harmless and `ResponseCompressionIntegrationTest` documents it rather than configuring around it. Pagination of the lists is, as the issue says, a separate contract decision and is not taken here: `GET /order` still returns every order.

**Compatibility.** No response shape changes. The customer listing and search are now ordered by customer ID and each customer's orders by order ID; before, both were heap order, which for the seed was ID order, so no client should notice, and it is the same guarantee the order and product lists gained in #8. The repository method the customer reads used (`findAll()`) is still inherited for anything else that needs it. The index changeset takes no lock that blocks application writes, so a rolling deploy is unaffected; an instance of the previous release keeps batch-loading orders while the new one joins them, and both read the same rows.

**Tests.** `ReadQueryCountIntegrationTest` loads `LargerDataset` on the shared container and, for each of the seven requests, asserts the statement count the strategy settled on (one everywhere), and that the response holds exactly the relationships the database holds, compared parent by parent against SQL rather than by totals: every customer's order IDs including the customer with none, every order's product IDs including the legacy orders and its customer ID, every product's order IDs including the ten in no order, and the search's customers against `WHERE name ILIKE`; each list is also checked for one root per row in ID order with no duplicates. A final test takes the counts on the seed and again on the larger dataset and asserts they are the same, which is the one-for-one growth criterion directly. Removing the entity graph from `CustomerRepository` makes four of these fail (12 and 2 statements), which is how they were shown to measure the strategy; the baseline table above is that run. `CustomerMapperTest` covers the ordering with unsorted input and the empty list; `CustomerServiceTest` now checks that both reads go through the one repository method sorted by ID, with no predicate for the listing and a blank query and a predicate for words. `OrderCustomerIndexIntegrationTest` and the changeset lists in `MigrationIntegrationTest` and `SchemaUpgradeIntegrationTest` cover the migration. `ResponseCompressionIntegrationTest` runs against the real port (the integration base now starts the servlet container as well as `MockMvc`, sharing the one context) and checks a large body is gzipped to less than half and decompresses to the plain bytes, that a client not asking gets the plain body, and the chunked-lookup detail above. The benchmark class is the measurement and is run by hand; its only assertion is that every request answered 200.

## #11 Building and publishing a Docker image through CI

**A multi-stage Dockerfile that builds from source.** The builder stage runs the committed Gradle wrapper on `eclipse-temurin:17-jdk`, the JDK the build's toolchain declares, so `docker build .` on any machine with Docker gives the same image with nothing else installed. Two alternatives were considered. Copying the jar CI had already built would make the image job faster (it recompiles, about a minute) and the Dockerfile three lines, but a local build would then depend on the host's JDK and on remembering to run `bootJar` first, and the image would no longer be a function of the source alone. Spring Boot's `bootBuildImage` (Buildpacks) needs no Dockerfile at all, but the base image and its JVM settings are chosen by the buildpack rather than recorded in the repository, and the first build is slow. The dependency resolution is its own layer, above the source copy, so an edit to `src` reuses the cached dependencies. Tests are not run inside the build: CI has already run `check` on the same commit, and the integration suite would need Docker inside the build.

**Runtime image: JRE on Alpine, non-root, layered.** The runtime stage is `eclipse-temurin:17-jre-alpine`, about 125 MB, with the boot jar extracted into Spring Boot's layers (dependencies, loader, snapshot dependencies, application) so a code change ships one small layer and the dependency layers stay cached in the registry and on the hosts pulling it. The process runs as a dedicated user and the JVM is PID 1 (exec-form entrypoint), so a `docker stop` reaches it as `SIGTERM` and Spring shuts down cleanly. Alpine was chosen over the Ubuntu-based JRE image for one practical reason: busybox gives the `HEALTHCHECK` a `wget`, where the Ubuntu image ships neither `wget` nor `curl` and would need an `apt-get` layer. JVM flags are left to the deployer through `JDK_JAVA_OPTIONS`, which the launcher reads, rather than baked in.

**Configuration through Spring's own environment variables.** The datasource is set with `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME` and `SPRING_DATASOURCE_PASSWORD`, which Spring Boot's relaxed binding has always accepted, so `application.yaml` is unchanged and `bootRun` still works against the README's `localhost:5433`. Inventing `DB_HOST`-style placeholders was considered and rejected: it would be a second way to say the same thing, and the standard names are what anyone deploying a Spring Boot container expects. The README points out the one trap, that the baked-in `localhost` is the container itself, and shows the two ways to reach a database by name: the compose file, and attaching the README's standalone `postgres` container to a user-defined network.

**Actuator health, exposed alone.** `spring-boot-starter-actuator` is added with only `health` on the web and component details hidden. It serves three purposes: the image's `HEALTHCHECK`, the CI smoke check's readiness signal, and the probe any orchestrator will want. `UP` is a stronger statement than a `200` from the API would be: it includes the DataSource ping, and because Liquibase runs before the web server starts accepting requests, a response at all means the migrations applied. The alternative, polling an existing API endpoint and adding no dependency, was considered and rejected because a GET on a list endpoint is both heavier than a ping and uninformative about why the service is not ready. `HealthEndpointIntegrationTest` pins the contract: `UP` against the real database, no component details, and `/actuator/env` and `/actuator/info` returning 404. A `DOWN` is a 503, so the health check fails rather than lies when the database goes away; checked by hand that a container pointed at a non-existent host exits and is reported unhealthy.

**One workflow, two jobs, publication only from trusted refs.** The image job runs after the existing build-and-test job (`needs`) on every pull request and every push to `master` or a `v*` tag. It always builds the image with `load: true` and runs the smoke test; the registry login and the push are two further steps guarded by `github.event_name == 'push'`. Pull requests therefore exercise the Dockerfile and the smoke test in full without any credential in scope, a failed test suite never reaches the image job, and a failed smoke test never reaches the push. The push is a second `build-push-action` call with the same context and GitHub Actions layer cache, so it is a cache hit that uploads layers rather than a rebuild. `packages: write` is granted to the image job only; the build job keeps `contents: read`. A separate `publish.yml` workflow was considered and rejected: one file keeps the dependency between validation and publication explicit (`needs`) instead of relying on `workflow_run` plumbing.

**GitHub Container Registry and the tag scheme.** GHCR costs no secrets: the workflow's own `GITHUB_TOKEN` can push to the repository's packages, and the package inherits the repository's private visibility. Docker Hub would have needed a personal access token stored as a secret. Tags come from `docker/metadata-action`: `sha-<short sha>` on every publish, which is the commit-addressable tag the issue asks for and the one a deployment should pin; `latest` for `master`; and the bare version for a `v<version>` tag, which costs one line now and means a release process can be added without touching the workflow. The image name is lowercased by the action, since the repository owner's name is not. Automated review on the pull request pointed out that the action's `latest` flavour defaults to `auto`, which adds an implicit `latest` to every stable semver tag, so tagging an older commit would have overwritten the `latest` that the README documents as master's build; `latest=false` leaves the explicit master rule as the only source of that tag.

**The smoke test is a script, not workflow YAML.** `.github/scripts/smoke-test.sh` starts `postgres:16.2` and the image on a private network, waits on the image's own `HEALTHCHECK` through `docker inspect` (with the interval shortened on the command line, so the production-tuned 30 s interval does not slow CI, and the start period lengthened to 120 s so that a slow runner cannot exhaust the retries while Liquibase is still loading the seed: the first CI run did exactly that, declaring the container unhealthy ten seconds in, where the faster local run had passed), then fetches `/actuator/health` and `/order/1` and checks the seeded description comes back. Reading the container's health status rather than polling from outside means CI verifies the `HEALTHCHECK` instruction itself. On failure it prints the application's last hundred log lines, and the containers and network are removed on every exit path. Review of the first version raised two points, both applied: the container names carried no run identifier and the script began by removing them, so two local runs would have destroyed each other's containers (names now carry the process ID and only that run's resources are cleaned up; verified by running two at once on different ports); and the application was started the moment the database container was, relying on the race being won, where Hikari fails fast and the PostgreSQL image spends its first seconds in `initdb`. The script now waits for `pg_isready -h localhost`; the `-h` matters because the image's initialisation runs a temporary server on the Unix socket only, which a socket-based `pg_isready` reports as ready. The compose healthcheck gained the same flag for the same reason. Keeping it as a script means the same check runs locally before a push; it was run here against a local build (passed, including after the first version wrongly fetched `/customer/1`, which has no lookup by ID; that 404 is why the script now reports a failed request through the same path that dumps the logs).

**compose.yaml.** Added as the shortest documented path to "run the image against PostgreSQL": a `db` service matching the README's prerequisites and an `app` service with `image` set to the published name and `build: .`, so `docker compose up` pulls and `docker compose up --build` builds. The database is also published on the host's 5433 so `bootRun` can use the same instance, at the cost of clashing with the README's standalone container if both run; the README says so.

**Left out.** No multi-architecture build (the runners and the likely hosts are amd64; `platforms` is one line when needed). No image signing or SBOM. No deployment: the issue excludes hosting, and the image plus a `sha-` tag is the hand-off point.

**Tests.** `HealthEndpointIntegrationTest` (three tests) in the integration suite. The image itself is tested by the smoke script, in CI on every pull request and before every publish, and locally against `docker build` and `docker compose up --build` while writing this.

## #10 Aligning the OpenAPI document and the documentation with the finished assignment

**The OpenAPI file is rewritten against the code, not generated from it.** `OpenAPI.yaml` was the assignment's own document and had drifted at every issue since #4: it lacked `GET /order/{id}`, `GET /products/{id}` and the `q` parameter, described the product list as one object rather than an array, let the product create carry an `id`, gave the product create no response body, and had no `products` on orders. Generating the document from the controllers with springdoc was considered and rejected: it would document whatever the code happens to do, which is the drift this issue exists to stop, and it would move a hand-maintained artefact the assignment supplied into a build output. The rewritten document keeps the original `info` block and the OpenAPI 3.0 version, so the tools that read it before still read it, and adds what the API now is: three tags, every operation with its real request and response schemas, the three problem responses as reusable components with examples copied from real responses, and `security: []` at the root, which is the standard way to state that the API has no authentication and the reason Redocly's recommended ruleset reported six errors on the old file. Every response schema sets `additionalProperties: false` and lists every property as required, because the DTOs always serialise every field; the point is that a field added to or dropped from a response fails the contract check below rather than passing unnoticed. The `Text` schema is shared by the three create bodies so the #4 rules (1–255 characters, not blank, no NUL) are written once. `uniqueItems: true` on the order's `products` expresses the #8 distinct-product rule in JSON Schema terms, since two `{"id": n}` objects with the same `n` are equal. The remaining Redocly warnings are deliberate: the server URL is `localhost` because that is where `bootRun` and the compose file put it, and the three list `GET`s document no 4xx because none exists for them.

**"Validates successfully" is enforced by the integration suite, two ways.** The choice was between a Node lint step in CI, a parse-only test, a hand-run check recorded here, and a contract test; the contract test was chosen because only it proves the document describes the running service, and it runs under `./gradlew check` so the local command and CI stay the same without adding Node to a Java pipeline. `OpenApiContractConfig` builds an Atlassian `swagger-request-validator` for the document and registers it with a `MockMvcBuilderCustomizer` as an `alwaysExpect` matcher on the suite's shared `MockMvc`, so every one of the hundred-odd requests the existing tests make is checked: the path and method must be documented, the status code must be listed for that operation, and the body must match the schema. Request bodies and parameters are not validated (`validation.request.body` and `validation.request.parameter` are set to `IGNORE`), because the 4xx tests send malformed and unknown input on purpose; what the contract has to say about those requests is which error they get, and that is checked. The actuator paths are whitelisted, by the text of the path-missing message because the library's path rules consult the matched operation and an unknown path has none; they are operational endpoints, and `HealthEndpointIntegrationTest` deliberately requests two that are not exposed. `OpenApiContractIntegrationTest` closes the other direction: it sends one request for every `operation × status` the document lists (twenty in all, the same sequence the README's worked examples use), lets the matcher validate each, and asserts that the set of responses reached equals the set the parsed document promises, so a status code nothing can produce fails as surely as one the code produces without documenting it. `OpenApiDocumentTest` parses the document with references resolved and asserts the parser has no messages; it runs without the application context, because the validator bean loads the same document for every test and a broken file would otherwise fail every integration test with a context error rather than one test with the parser's message. All three were watched failing before the document was fixed: the matcher on the old document's bodiless `POST /products` 201, the contract test on the missing paths, and the parser on a reference to a misspelt schema. The library is a test-scope dependency pinned to 2.44.9, its parser is `swagger-parser` 2.1, and it carries no transitive change to the application. The whole suite grew by about two seconds, most of it schema-validating the 2 MB order listing.

**README.** Restructured around what a reader does: a clean-checkout quick start whose four commands were run in that order on a fresh clone of this branch; the Windows differences gathered in one section, each checked on this machine (the wrapper's committed `100755` mode and the LF rule in `.gitattributes`, `gradlew.bat`, `JAVA_HOME` for a wrapper on a JDK newer than 23, backtick continuation, `curl.exe` and PowerShell 5.1's handling of double quotes in a JSON argument, Git's path-length limit, and that the smoke script needs Git Bash); the data model and the API table as they are after #8; the error contract and the search semantics in prose with the detailed reasoning left in this file; worked examples for every assignment task with the real responses pasted in; and an assumptions section that lists the decisions a reviewer is most likely to question with the issue that records each. The original task text is kept at the end rather than deleted. `./gradlew clean check bootJar` was already the documented local command and is what `ci.yml` runs, so that criterion needed verification rather than change. The Docker and CI sections from #11 are unchanged except for a sentence on the contract check.

**Data-generation guidance.** `utils/README.md` told the reader to "hack the liquibase changelog or drop and recreate your database" after regenerating `data.sql`. Both are what a production database must never see: Liquibase checksums every applied changeset, so an edited `2-data` stops every existing deployment at start-up, and dropping the database is losing the data. The guidance now says generated data goes into a new numbered changeset, as every change in this project has, and lists what the script does not do: it starts IDs at one (so its output collides with the seed unless the IDs are moved or dropped, and the sequences then need the #3 repair), it does not escape apostrophes, and it knows nothing about products. The script itself is left alone; changing it is outside this issue and the seed it produced is applied everywhere.

**Verification on a clean checkout.** The branch was cloned into an empty directory on this Windows machine and the README followed verbatim with Git Bash, Docker Desktop and `JAVA_HOME` on JDK 21 (Gradle's own requirement; the Java 17 toolchain is resolved by Foojay): `./gradlew clean check bootJar` (both suites green, jar produced), the PostgreSQL container started with the README's command, `./gradlew bootRun`, and every worked example run with `curl` against it, whose output is what the README shows. The PowerShell variants were run in PowerShell 5.1 to confirm the quoting advice. One Windows trap was found by this run and added to the README: a clone under a long directory prefix fails with "Filename too long" until Git's `core.longpaths` is enabled.

**Automated review on the pull request** raised four points, all applied. The creates already answered 415 as a problem document for a non-JSON `Content-Type` (unit-tested since #4) and the document did not say so; a reusable `UnsupportedMediaType` response is now on the three `POST`s and the contract test sends a `text/plain` body to each, which also meant adding `validation.request.contentType` to the request-side checks the matcher ignores, since the wrong media type is the point of those exchanges. The first draft of the data-generation guidance said a new changeset plus the changeset-list assertions would make the suite pass, which is false: `SeedDataIntegrationTest` and `CustomerSearchIntegrationTest` pin the seed at 100 customers and 10,000 orders and several tests take 10,000 as the last seeded order ID, so the guidance now separates a local database (load the SQL directly with `psql`, outside Liquibase) from data every environment should hold (a changeset, and the pinned tests updated in the same change). The same draft offered "remove the `id` columns" as an alternative to offsetting the IDs, which would attach every generated order to the first `N` seeded customers because the script writes literal `customer_id` values; only the offset is recommended now. Finally, `maxLength: 255` counts code points where `@Size(max = 255)` counts UTF-16 units (the mismatch #4 recorded and chose to keep); the `Text` schema now says so rather than the validation being changed, since the request side of the contract is documented, not enforced, and the application rule is #4's decision.

**A second, local review** tightened three more things. Request validation had been switched off for every exchange, so a request schema could drift from a DTO while the suite stayed green; it is now on, and a whitelist rule ignores request-side findings only when the response is a 4xx (`isRequest()` and `responseStatusTypeIs(CLIENT_ERROR)`), so every request the server accepted must match its documented schema and the deliberately bad ones are judged by their response alone. Checked by setting `Text.maxLength` to 3 for one run: the 201 exchanges failed on the request body and nothing else changed. The 415 wording said anything but `application/json` is rejected, where Spring's JSON converter also accepts `application/*+json`; the document says so now, with `application/json` as the one documented type. And the `Text` pattern used `\s` for blank where the server uses `@NotBlank`, which is Java's `trim()`: ECMAScript's `\s` includes the non-breaking space and the other Unicode spaces, which `trim()` does not strip, and excludes control characters below U+0020, which it does. The pattern is now `[^\u0000-\u0020]` for the required character, which is `trim()` exactly, and the description states the rule in words.

**Left out.** No pagination contract (recorded as an open decision since #9). No OpenAPI-driven client or server generation; the document is a contract and a reference, and the contract test is what keeps it one. No lint step in CI: Redocly's recommended ruleset was run by hand (valid, four intentional warnings) and is noted here rather than wired in, since the suite already fails on any document that does not parse.

**Tests.** `OpenApiDocumentTest` (parses with no messages), `OpenApiContractIntegrationTest` (every documented response reached and valid), and, through `OpenApiContractConfig`, every existing integration test now also asserts that its responses match the document.

## #23 External review of the submission

**What the review said.** An external review of `master` after #10 and #11 found no functional gaps and six points of presentation and precision: the two documents are long; two explanations under #9 are imprecise; `spring.jpa.open-in-view` was left at its default; `Customer` still carried `@Data`; the README led with the JDK route; and two claims outran their evidence. Each was checked against the code before being acted on, and all six held.

**Open EntityManager in View is now off.** `spring.jpa.open-in-view: false`. Every response has been mapped inside its service transaction since #4, so no request needed the persistence context Spring Boot otherwise keeps open for the whole web request; the default was only ever a latent path for a future controller to trigger a lazy load outside the boundary, which would issue a statement `ReadQueryCountIntegrationTest` cannot see because it counts inside the service. With the setting off such a load throws `LazyInitializationException`, which makes the boundary enforced rather than observed. The suite passed unchanged, which is the evidence that nothing relied on the open session.

**`Customer` drops `@Data`.** #7 left it with the note that nothing hashed a customer and #9 would revisit; #9 put no customer in a set, so it stayed. It now uses `@Getter` and `@Setter` like `Order` and `Product`, with identity equality, so the three entities follow one rule and a future `HashSet<Customer>` or a log line cannot initialise the lazy `orders` collection through a generated `hashCode` or `toString`. No test compared customers by value, so none changed.

**Two explanations corrected, no code changed.** The #9 paragraph on keeping the read-only transaction said it gave the mapping a "consistent snapshot"; under PostgreSQL's default `READ COMMITTED` it does not, and the paragraph now says what the transaction provides (the persistence context) and what makes the reads consistent (each is one statement). The product-list paragraph said a narrow projection needed a second statement; a scalar projection over the same left join is one statement, and the paragraph now weighs that option by its real cost, grouping code instead of entity loading, and records why it was still not taken. **Claims cut to what the tests show.** The README said the contract check meant the document "can neither drift from the code"; it now says the check covers the exchanges the suite makes and not every input the API could receive. The statement about one statement per read now separates what it fixes (round trips) from what it does not (rows, memory and bytes, which grow with the unpaginated lists), and the "lists are not paginated" assumption says the same.

**README leads with Docker.** The quick start is now `docker compose up --build`, which needs Git and Docker only, builds the submitted checkout rather than pulling from a registry the assessor may not have access to, and is followed by a five-request sequence (create a product, create an order, read both and search for the customer) with the real responses.
